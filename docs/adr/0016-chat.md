# 0016 – Chat between the participants

* Status: Accepted
* Date: 2026-11-16
* ASRs: F-7, Q-1, Q-3, Q-12

## Context

Participants need a quick, informal way to talk to each other and to the
exercise leader, next to the formal reports. The brief says only "a chat
function between the participants"; the shape is ours to choose. It should
fit what is already there: shared group accounts, a shared leader role,
SQLite, pages that work without JavaScript, and a strict CSP.

## Decision

* **Conversations.** One shared conversation, *Everyone* (all groups and
  the exercise leaders), plus a direct conversation for every pair of
  parties: group ↔ group and group ↔ exercise leader. Conversations are
  not created or managed; they exist implicitly.
* **Parties, not persons.** A party is a group account, or the exercise
  leaders collectively – the same model as report receivers
  ([ADR 0004](0004-roles-and-group-accounts.md)). All leaders see and
  answer the conversations with the leader; a leader's own display name is
  shown on each message.
* **Privacy of direct conversations.** Only the two parties can read a
  direct conversation. The exercise leader has **no** oversight of
  group-to-group chat, and the administrator has no chat at all. The page
  states who can read the conversation being shown.
* **Authorisation by construction.** A conversation key is always derived
  from the *requesting user's own party* and the peer in the URL, so there
  is no way to name a conversation one is not part of.
* **Messages** are plain text up to 2 000 characters, immutable, with
  sender and time set by the server. No attachments, no formatting, no
  deletion.
* **Storage.** Two SQLite tables added by migration 2: `chat_messages`
  (with a monotonically increasing sequence number used as the paging and
  polling cursor) and `chat_read` (last sequence number seen per party and
  conversation, for unread counters).
* **Transport.** Sending is an ordinary form `POST`. With JavaScript, the
  page polls `GET /api/chat/{peer}?after=<seq>` every 4 seconds and appends
  new messages, built from a `<template>` with `textContent`; without it,
  reloading the page shows new messages. The unread counter in the menu
  rides on the existing 30-second poll.
* **Limits.** 20 messages per user per minute; the newest 100 messages per
  page with a link to earlier ones.
* **Logging.** The audit log records that a message was sent (who, which
  conversation, sequence number), never its text.
* **Switch.** `-chat=false` / `GR_REPORT_CHAT=off` removes the feature.

## Alternatives considered

* **WebSocket or server-sent events.** Instant delivery, but one
  long-lived connection per open page, which conflicts with the server's
  read/write time-outs and needs reconnect logic; a 4-second poll of a
  small JSON document is simple and enough for an exercise.
* **Per-person chat accounts.** Chat inherits the shared group accounts;
  personal identities are a larger change (see ADR 0004).
* **Leader can read all conversations.** Useful for exercise control, and
  consistent with leaders being able to read all reports. Rejected as the
  default because participants would reasonably expect a direct chat to be
  private, and silent oversight is worse than none. If oversight is wanted
  it should be added as an explicit, visible setting.
* **Free-form rooms.** More flexible, more to administer; the fixed set
  covers the described need.
* **An external chat server (Matrix, IRC).** Another service to run and
  secure on an isolated exercise network.

## Consequences

* A message reaches other open pages within about 4 seconds; unread
  counters elsewhere update within 30 seconds or on the next page load.
* With several leader accounts, a message read by one leader is marked
  read for all of them.
* Members of a group share its conversations; there is no private channel
  between individual persons.
* Chat history is stored unencrypted in the database like everything else;
  whoever can read the database file can read every conversation.
* Messages cannot be withdrawn. Misuse is handled by disabling the account
  or switching the chat off.
* Polling adds a small, constant request load per open chat page
  (one request per 4 seconds).
